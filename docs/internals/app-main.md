# App main process

The process boundary, the indexing pipeline table, re-indexing, whisper resolution, packaging traps, and the MCP endpoint.

> Moved out of `CLAUDE.md` on 2026-08-15, verbatim. Every number here is a measurement
> taken from a real recording or a real run — not an estimate. Re-measure before changing one.

electron-vite + React + TS. Three source roots with a hard rule between them: **`src/main` is the only process that may touch the library, the store, or native modules.** `src/preload` is a typed `contextBridge` exposing `window.deskrag`; `src/renderer` sees only plain serializable DTOs.

- **`src/shared/types.ts` is the contract** — DTOs (`FrameHitDTO`, `ResultDetailDTO`, `SettingsView`, …) plus the `IPC` channel-name map, so main and preload can't drift. It imports nothing from Node or `deskrag`; both sides depend on it. Changing an IPC shape means changing it here first. **`shared/evidence.ts` is the one module there that exports RUNTIME values** — the lane-name table and the tie rule, read by BOTH the Search screen and the MCP `search_experience` tool, which describe one retrieval to two audiences and must not drift. `@shared/` is aliased in main, preload and renderer alike so the import resolves in all three, but the ROOT `tsconfig.json` needs its own **exact-path** entry per module (it is NodeNext and cannot follow the app's bundler-style wildcard) — a new shared module that a root test imports needs a line added there.
- **`DeskRagService` (`main/deskrag-service.ts`) is the single owner of the library** — opens the `DualStore` + `BlobStore` under the app data dir, builds providers from settings, runs the record lifecycle, auto-indexes (segment → represent) on stop with per-stage progress events, and hydrates search hits into DTOs.
- **THE INDEXING PIPELINE IS A TABLE, NOT A `push()` ORDER, because the order IS the interface and a second hand-written copy of it went stale.** `index-plan.ts` declares every stage's id, label, `gate`, `needs` and `reindex` scope; `planStages(facts)` returns the ordered selection as a VALUE, so the ordering is assertable in the ROOT suite with no store, no Electron and no model. `index-run.ts` holds the bodies as a `Record<StageId, StageRun>` — the compiler finds a stage that was declared and never implemented, the same device as `showLabels` on `TrackLaneDTO` — plus `runStages`, which takes its runner map as a parameter so the driver is testable without a store. Both modules import no `electron`, which is the condition for a root test to reach an `app/src/main` module at all.
  - **The array IS the order; `needs` is CHECKED, never obeyed.** A topological sort of this DAG is not unique, so its tiebreak would have to be table order anyway. `needs` states the reason each stage sits where it does and `stageOrderViolations` turns what used to be a prose comment into something a test fails on. A dependency absent from a plan is not a violation — gated stages drop out on a default install, and composing still has to follow whatever text stages actually ran.
  - **`runStages` OWNS the progress axis, because the two callers count different things** — the record path counts stages, a re-index counts recordings with the stage folded into the label. Both reporters set `this.downloading`, so a weight download inside a stage rewrites its label; the old rebuild never set it, and now actually runs transcription. `ctx.report(label)` also fixed a silent bug: `run` used to return `Promise<unknown>` and the driver DISCARDED it, so Composing's `— N levels, N nodes` line was computed on every run and emitted on none. Trace only worked because it reached for the service's emitter from inside its own closure.
  - **`tolerateFailure` is data on the spec, not a hand-rolled try/catch**, and it is set on `transcribe` alone — the only stage that downloads on the indexing path, with Trace running after it.
  - **`reflect` is the ONE MODEL-ONLY stage, and the only one whose absence costs a whole artefact rather than its prose.** Every other derived row is a measurement — a digest names a gesture, a caption describes a screen, a rollup names a stretch of work — and *none of them can say a session went badly*. That is the gap a habit inherits: built from those rows alone, a habit can only ever describe a task as though it went smoothly. So a reflection is a JUDGEMENT, which is why it has no structural fallback the way composing does: a rollup can honestly name a group of actions, but nothing templates "this stalled". With no summary model there is no note, the ladder draws the stage skipped, and `skipReason` says why.
    - **It runs AFTER `compose` and needs it.** `reflectionBriefFor` (pure, root-tested) reads the composed ROOT's own children as the steps — a 40-minute recording is hundreds of actions and a handful of tasks, and the question is the shape of the session. Fewer than two steps and it returns **null**: a note over one step can only restate it, and would still cost a model call per recording. A step elided down to a leaf has no summary row at all (`composeLadder` adopts a lone child rather than wrapping it), so it is named from its **digest** before any placeholder.
    - **The prompt states each step's SHARE of the session, not just its seconds.** Time and action counts are the entire evidence for "what stalled", and a model dividing a dozen pairs of numbers in its head gets some of them wrong — quietly, and in the direction of whichever step it had already decided to name. A zero-length session omits the share rather than printing 0%.
    - **The gate fact is `summarizer` but `stageWorld` reads `providers.reflector`.** One setting builds two objects (different briefs, different reply shapes), so they are null together; the gate asks the object the stage actually uses, because a gate that passes on a *different* object's presence is exactly how a stage runs with a null provider and writes nothing. `plannedFacts` answers the same question from `summaryProvider !== "none"` — the two derivations of one truth that must agree.
    - **Measured, on a real recording and a real 30B model** (`npm run probe:reflect`, 2026-08-20, muse-glimmer:30b-mlx over a 32-frame session): the note named only steps that were in the brief, quoted the share and action counts it was given ("31 actions over 33.5s"), and **declined both invitations to invent** — "No clear stall is visible in the record" and "The recording does not show an alternative order that would have been faster". That decline is the property the prompt is written for and the reason `better` is allowed to say nothing; a model asked for advice will otherwise always produce some.
    - **It catches its own failure instead of being added to `tolerateFailure`.** A daemon that is down is one chat call away from a missing opinion; `tolerateFailure` exists for transcribing, which downloads weights mid-run. Widening that list would have let a missing note take Search index and Trace down with it. The stage still SAYS what happened — the detail survives on the stage record.
  - **`session_reflection` is a DERIVED_SESSION table keyed on the composed root segment, and it carries no timestamp of its own.** Hanging off `segment(id) ON DELETE CASCADE` is what makes `deleteSegmentsBySession` purge it for free, so a re-index rewrites the note under the providers configured *now* rather than leaving a stale opinion on a rebuilt hierarchy — and the note inherits its session's `t_mono` through the root rather than recording a wall clock that describes the indexing run. Its `source` is the MODEL that wrote it (`"ollama qwen3:30b"`), **not** `segment_summary`'s `'llm' | 'template'`: there is no template path, so `'llm'` would carry no information, and what a reader needs is which model — a reflection is an opinion and its author is the whole of its weight.
- **INDEXING IS A DURABLE QUEUE (`index_job`), and that split `RecordingState` in half.** Capture and indexing used to be ONE awaited call: `stopRecording` claimed `state = "indexing"` and then `await this.index(sessionId)` *inside* the `recording:stop` IPC handler. Since `startRecording` refuses whenever the state is not `idle`, the record button was dead for the whole pipeline — **measured on a real recording, 21m 51s**: Captions 14m 16s, Frame patches 5m 00s, App captions 2m 31s, and every other stage under three seconds. (That App-captions stage has since been retired and the caption stages take a width-capped image; the split it forced is unaffected — indexing is still minutes and recording is still real-time.) Stopping now enqueues and returns, **measured at 148ms**, and `RecordingState` is `idle | recording`. **Do not add `"indexing"` back**: it being a value of that enum is exactly what made the two mutually exclusive.
  - **Three modules, split by what they need.** `index-queue.ts` is the POLICY — `nextRunnable`, `mustPurge`, `initialStages`, `jobProgress` — pure functions over job rows, so the pause rule is assertable in the ROOT suite with no store, no Electron and no model. `index-worker.ts` is the drain loop, which needs the store and the providers and takes both through injected deps. `index-graph.ts` projects the ladder for the screen. Same division as `session-tracks.ts` versus `track-view.ts`.
  - **`index_job` is OPERATIONAL — a fourth bucket in `schema.ts`, and the classification is load-bearing.** The queue DRIVES a re-index, so a purge that cleared it would delete the job currently running. It is not captured either: losing it costs pending work, which is re-enqueueable, never a recording, which is not. `kind`, `payload` and `progress` are opaque to `store/` on purpose — what a stage IS belongs to the app, the same seam that keeps `store/` free of `represent/`. **Verified the `transcript_clip` way**: a copy of the real 24-table `app.db` opened with the new code gained `index_job` and **no other table's row count moved**.
  - **Ordering is by `rowid`, not by the ULID primary key.** `enqueued_at` is a millisecond and `reindexAll` fans out one job per recording inside a single loop, so every job in a library rebuild shares a timestamp and the TIEBREAK is what actually orders it. `ulid()` randomizes its suffix within a millisecond rather than incrementing — so "oldest recording first", which `rebuildGraph` depends on, would have come out shuffled every time. Caught by the test, not by reading.
  - **Enqueue is idempotent per (kind, sessionId) while a job is live**, which is the queue's own version of the synchronous state claim in `stopRecording` (measured: 28 segment rows, 14 duplicated, from one double `index()`). The predicate is `session_id IS ?`, not `=`: library-scoped jobs have a NULL session and `NULL = NULL` is NULL, so a plain equality would let every trace rebuild enqueue a duplicate.
  - **INDEXING YIELDS TO RECORDING, BETWEEN STAGES AND NEVER INSIDE ONE.** A dropped frame cannot be re-recorded; an index rebuilds from the blobs whenever. `runStages` takes a `gate` awaited at the top of each iteration — mid-stage would leave exactly the half-written derived rows the purge exists to clean up. **The consequence has to be disclosed, and was not until it was seen on screen**: the slowest stage takes 14 minutes, so a job already in flight keeps running for that long after a recording starts. `holdMessage` therefore has two sentences — "Recording — indexing pauses as soon as the current stage finishes" versus "Paused — recording in progress". Reporting `held: null` whenever a job was mid-flight (the first version) meant the screen showed a job running beside a live recording and said nothing at all.
  - **`emitState()` also emits the queue**, because `IndexQueueDTO.held` is a function of whether capture is running — starting a recording changes the queue's answer without touching a job row. Emitting only the recording state left the renderer holding a snapshot that still said `held: null`: the queue reported the hold correctly over IPC and the SCREEN showed no banner. They are emitted together so they cannot disagree.
  - **Purge-or-not is DERIVED from `(kind, attempts)`, never stored.** A manual re-index always purges; any retry purges (`attempts > 1`, since the count increments at claim); a first-attempt record job does not, because nothing is derived yet. No flag on disk can then disagree with the situation it describes — and `requeueRunningJobs` re-queues the payload byte-identical, which is what keeps it opaque to the store.
  - **A `running` row at startup is a CRASH, and the only thing that can produce one.** `recover()` re-queues it with its attempt count intact and gives up at 3, because a job that takes the app down on every attempt is otherwise an infinite loop across launches. **Resuming mid-plan is not offered and must not be added**: every stage appends. Exercised for real — a probe that killed the app mid-`digest` three times produced `failed / attempts 3 / "Abandoned after 3 attempts"` with a ladder showing exactly which stage it died in. The old design could not say a crash had happened at all.
  - **`before-quit` MUST await `service.pendingStop()`.** It is synchronous, and `stopRecording` deliberately returns the UI to idle *before* it shuts the producers down, stamps `ended_at` and enqueues — that tail is what the fast return costs. Closing the store through it loses all three: **measured by driving the app, quitting ~150ms after pressing stop left a real 6-frame recording with `ended_at` NULL and no job**, on disk and invisible to everything. `adoptUnclosedSessions()` recovers sessions already stranded that way — a session with no end stamp at *startup* cannot be recording — and stamps the end from the last captured event rather than from `Date.now()`, which would claim the recording ran until the app next launched.
  - **The ladder shown for a QUEUED job is PREDICTED, not stored.** `plannedFacts` reads settings the way `buildProviders` does, so a waiting job already says which stages its configuration will skip and why. Computing it on read rather than writing it at enqueue keeps the stored `progress` meaning exactly one thing — what actually ran — and covers rows written by an older build. Before this, five jobs queued behind one running job all read `0/0 stages` beside an empty diagram.
  - **Two push channels, deliberately.** `indexing:queue-event` is a full snapshot on transitions; `indexing:tick-event` carries the running stage's `detail` AND its `progress`, and fires PER FRAME in the patch stage. One channel would re-serialise the whole queue at that rate. This also retired `IndexingProgress`, whose `done/total` meant stages on the record path, recordings during a re-index and *frames* inside one stage — all plotted on one 6px bar, which therefore changed scale mid-run. The JOB bar counts stages and only stages; a stage's own units are `StageProgress`, a separate meter on its row.
    - **`detail` and `progress` ride SEPARATE ticks, each null on the other's**, so a consumer must apply only the field the tick actually carries. Folding a tick in wholesale lets a progress update erase the download line whisper had just written.
    - **THE SNAPSHOT MUST BE EMITTED AFTER ITS WRITE LANDS.** `indexQueue()` READS `store.listIndexJobs()`, and `persist` writes through a chained promise — so emitting synchronously after it publishes the previous ladder. Measured: the screen ran a whole stage behind, `captions` reporting 2/4 while the DOM still marked Frame patches running. `persistAndEmit` is the only correct pairing.
    - **A stage's `elapsedMs` is computed WHEN THE SNAPSHOT IS BUILT**, i.e. on transitions — so it is frozen at `begin` for the whole of a running stage and the renderer must run its own clock off `startedAt`. `StageProgress.at` exists for the same reason: a rate measured against a live clock climbs while a unit is in flight and snaps back when it lands.
- **RE-INDEX MEANS RE-INDEX: purge everything derived, then run the whole plan.** `reindexAll` is NOT a subset of the record path — being one is exactly how it went stale. Per recording, oldest first: `store.purgeDerived(id)` then `runStages(reindexPlan(facts).perSession, …)`, then ONE `rebuildGraph` at the end. Re-segmenting is safe now and was not before: the old worry was new segment ids orphaning captions and transcripts, and the purge removes those first. `trace` is the one `library-finisher` — a graph accretes, so re-lifting a session into a graph that still contains it double-counts its `observations`.
  - **The purge is what makes a second pass safe, and the bare write paths are why.** `putRegions` and `putSegmentVectors` are bare inserts/adds — `putRegions` even mints a fresh `ulid()` per region — so a second pass over live rows APPENDS a whole second set, and duplicate vectors that still have SQLite rows are not orphans, so `reconcile()` can never prune them. (`putFramePatches` already deletes-then-adds.) **Measured on a copy of a real 13-recording store, re-indexed TWICE end to end: every derived count identical, and every vector table exactly 1×** — 683 action segments against `digest` **683** and `behavior` **683**, 63 summary rows against `summary` **63**. Without the purge the region table alone would read 15222 rather than 7611. (That measurement predates the removal of the single-vector image lane, so its `frame_image`/`region_image` rows no longer exist; the write paths it names still do.) An image-path run took ~10 minutes over 546 frames, which is the other thing to know before pressing the button.
  - **It rebuilds with the providers configured NOW, and that is destructive.** Same store, re-indexed with no captioner/whisper/image provider: `segment_app_caption` 454 → 0, `transcript_clip` 54 → 0, and the caption/app_caption/transcript vector tables all → 0 (as did `frame_image`/`region_image`, before that lane was removed). `app_caption` has since been retired too — its Lance table is dropped on open and nothing writes `segment_app_caption` any more, but **the table stays classified derived precisely so this purge still empties the rows every pre-retirement store is holding**. Recomputable from blobs still on disk, but only by a run that has the provider — which is why Settings confirms first and names which of the three will not come back. Captured rows are untouched (`session`/`event`/`blob`/`frame`/`ax_snapshot` all identical), and leaf actions came back at exactly 683 either way: segmentation is deterministic, only the composed levels differ (96 summaries → 63, Process being model-only).
  - **`CAPTURED_TABLES` / `DERIVED_SESSION_TABLES` / `DERIVED_LIBRARY_TABLES` in `schema.ts` are a GUARD, not documentation.** A root test reads `sqlite_master` and fails if any table is in none of them, so adding one forces a decision about whether a re-index must clear it — an unlisted table is precisely how a purge comes to leave something behind, and nothing else would notice. `transcript_clip` is the one that does not cascade (its FK is to `session`, not `segment`) and must be deleted by name.
  - **A registered namespace whose Lance table is NOT ON DISK must be a no-op to delete, not an error.** Measured on the real store: 12 rows in `vector_space` against 11 directories in `lance/`, because selecting a provider registers the space and the table only materializes on first write. `deleteByIds` opened it and threw `Table '…' was not found`, which took down the whole re-index — and took `deleteSession` down the same way, since both walk EVERY registered space rather than only the ones a session has vectors in. Fixed in the Lance layer, where "delete from a table that was never created" has already achieved its goal.
- **Everything optional is gated, never assumed.** Stage gates read `StageFacts` (booleans only, so `planStages` stays pure): frame/region need an image embedder, captions a captioner, transcripts BOTH audio in the recording and a whisper *binary* on the machine — see below; native producers (`uiohook-napi`, `active-win`, `sharp`) are `await import()`ed with `/* @vite-ignore */` inside try/catch so a missing module disables one signal instead of failing startup. `capabilities()` mirrors this to the renderer for UI gating.
- **An EMPTY whisper setting means "default", never "off"** (`main/whisper.ts`). `modelPath: ""` → the managed GGML (`MODELS.whisper`, `ggml-base.en-q5_1.bin`, 57MB, downloaded on first transcribe like every other weight); `binaryPath: ""` → `whisper-cli` on PATH. The version that read `""` as "no whisper" is what made transcription unreachable for everyone: clearing the Settings field skipped the transcribe stage, and since **only that stage fetches the model**, the automatic download never ran either — presenting as "the download is broken" when the real state was "transcription is disabled". `load()` normalizes a blank binary back to the default; `set()` deliberately does **not**, because it runs on every keystroke and snapping a cleared box back mid-edit would fight the typist — resolution happens at spawn time instead.
  - **Availability is `EnvInfo.whisperConfigured`, never a capability.** `Capabilities` reports configured *intent*, and since no whisper setting can express "off", a `transcript` member could only ever be `true`. It was removed rather than left as a constant. What can still be missing is the binary, which is a fact about the machine — probed with `which`/`existsSync`, and re-probable from Settings because installing it mid-session otherwise changes nothing the app notices.
  - **Transcribing is the ONE stage allowed to fail without failing the run.** It is the only stage that downloads on the indexing path, and it runs **before Trace** — so a network failure, a checksum mismatch, or a binary that vanished after the probe would abort indexing and take the trace graph with it. A session with no transcript is still a session; a session with no graph is one the executor cannot use. `ModelFilesMissingError` gets its own message: a set "Model directory" disables managed downloads *by design*, so the GGML must be placed there by hand — reaching around the override would break the only promise that setting makes.
  - **A weight download rewrites the running stage's label.** `ModelDownloadProgress` has its own IPC channel because a download can start from search, but the indexing screen renders `IndexingProgress` — so 57MB fetched inside Transcribing was a silent stall indistinguishable from a hang. The stage folds it into its `detail`, deliberately NOT its `progress`: a download is not the stage's own units, and driving Transcribing's audio-clip meter with 57MB of weights would show the stage advancing through work it has not started. No new IPC.
- **A habit is AUTHORED — the fifth `schema.ts` bucket — and no purge, re-index or trace rebuild may touch it.** The four existing lists answer "where did this come from"; `AUTHORED_TABLES` answers the question a purge actually asks, CAN IT BE REMADE. Captured rows are what everything else is re-derived *from*; derived rows can be discarded and rebuilt; `index_job` can be re-enqueued, and its own comment says so ("losing it costs pending work, which is re-enqueueable, never a recording, which is not"). A habit's title, prose and samples toggle are the exact inverse of that sentence. Filing it under OPERATIONAL would have put the one table that must never be lost inside the list that means "safe to lose". `state` and `doc` are opaque to `store/`, the `index_job.payload` seam.
  - **A habit's binding is a RECORD OF A PAST ACT, not a pointer.** A route's id is the de-duplicated sequence of place labels it passes through, so one extra app hop renames it, and `rebuildGraph` replays everything from zero on each re-index. `bindHabit` (`main/habit-bind.ts`, pure) resolves a stored binding against the routes that exist now: exact key, else a **strict majority** of the bind-time `sessionIds`, else orphaned. The majority rule is not a tuned threshold — `frequentRoutes` gives each recording exactly one route key, so the sessionIds PARTITION and more than half of a set lies in at most one part; a majority has at most one winner *mathematically*. A tie DECLINES, for the reason `trace/identity.ts` declines to merge on ambiguity. **Nothing in `bindHabit` writes**: a re-bind is disclosed and stays disclosed until a person confirms it, or the habit's own record of where it came from becomes unfalsifiable.
    - **CONSEQUENCE, and it caught two callers: the STORED key is stale by design, so every consumer must ask `bindHabit` for the LIVE one.** Removing the recorder from the graph re-keyed every route at once and exposed both. `unclaimedRoutes` was fed `binding.routeKey`, so the kept habit — correctly rebound to `Calculator → TextEdit` — had its own route sitting in the proposals list beneath it, one click from becoming a second habit for one flow; it is now fed both keys, since the stored one is still right whenever the graph has not moved and an unbindable habit has no live key at all. `scripts/transfer-probe.ts` matched the raw key against route ids and reported **every kept habit orphaned**, printing "Re-bind it first" instead of measuring anything; it now calls `bindHabit` and discloses which route it read. `duplicateHabits` was already correct. **Grep for `binding.routeKey` before adding a third reader.**
  - **`bind_session_ids` lives inside the `doc` JSON and is deliberately NOT a foreign key.** An FK would cascade on session delete and take the user's prose with it — destroying exactly the evidence the app has to disclose ("written from 5 recordings, 1 of which is gone"). That cascade is right for `trace_edge_source`, whose whole job is to be navigated back to, and which is also why a deleted recording lowers `route.count` immediately with no rebuild.
  - **THE SAME WORK WALKED SLIGHTLY DIFFERENTLY IS ONE ROUTE, AND A DETOUR COSTS TWO INSERTIONS.** `frequentRoutes` groups by exact equality of the place-label sequence, which is right about what a route IS and wrong about when two of them are one: a side trip renames the key, so identical work lands as two routes of ×1 and neither ever looks like a habit. `route-cluster.ts` merges near-misses, and the rule was **chosen by measurement, not by taste** — `npm run probe:routes` over a six-recording corpus, where the same task recorded three times (once through Finder) keyed as `… → Calculator → TextEdit → Electron` ×2 and `… → Calculator → TextEdit → Finder → TextEdit → Electron` ×1. **The gap is +2, not +1: leaving and coming back inserts both the place you went to and a second copy of the place you returned to.** The rule shipped at budget 1 before the corpus existed and merged nothing at all — which reads as "the rule does not fire", not as "the rule is off by one". Only a one-way hop that permanently changes the tail costs 1, and people come back.
    - **The insertions must be INTERIOR — same first place, same last place — because containment cannot tell a detour from a TRUNCATION.** `A → B` is contained in `A → B → C` at a gap of 1, but that walk did not take a side trip: it stopped one state short. Folding it in publishes a route as walked three times when one of the three never finished. A route is work with an outcome; two walks that end somewhere different did not do the same work, however much of the middle they share. This was caught by an existing test, not by inspection.
    - **`lcs ≥0.80` and `jaccard ≥0.80` merged the same pair on that corpus, so containment is not the only rule that works — it is the one that cannot fail QUIETLY.** Loosening the float to `lcs ≥0.60` fused two unrelated browsing sessions (LinkedIn-then-news with news-then-Fox-then-Business-Insider). Containment refuses that *by construction*: it only ever merges walks where one is a subsequence of the other, so it can never claim a merge between two paths that genuinely diverge. A float can, and by how much is invisible until somebody reads the output.
    - **Merging is COMPLETE-LINKAGE and declines on ambiguity.** Single linkage chains — A merges with B, B with C, and A and C end up in one route having never been compared. Every member must be compatible with every other. A route compatible with two mutually-incompatible clusters stays on its own and both clusters record that they wanted it: `trace/identity.ts` refusing to merge on an ambiguous match, one layer up.
    - **It merges WHOLE ROUTES, which is what keeps `bindHabit`'s majority a proof.** A session was never in two routes, so it cannot be split across two clusters — the partition survives by construction rather than by care. `test/route-cluster.test.ts` asserts it anyway, and `probe:routes` prints it per rule, because nothing else would notice if it stopped being true.
    - **What was merged is DISCLOSED, never smoothed away.** `FlowRouteDTO.variants` carries each folded walk, its recordings and its extra hops; the route list, the proposal row and `## What this evidence does not say` all say so. The merge inflates `count`, so a route reading "recorded 3 times" while one of the three detoured would be claiming more agreement than was found.
  - **An orphaned habit still produces a usable FILE.** Orphaning is routine rather than exotic, so the doc carries `stepsSnapshot` — the record as it last rendered — refreshed at every moment the habit is written anyway and **never on a read**. A snapshot that refreshed itself when looked at would be indistinguishable from a live render, which is the one distinction an orphan has to make.
  - **A HABIT CARRIES ITS OWN VERSION, IN THE `doc` JSON AND NEVER IN A COLUMN.** `schema.ts` is `CREATE TABLE IF NOT EXISTS` with no migration step, so an existing table's *shape* can never change — which is the whole reason the opaque `doc` column exists. `StoredHabitDoc.version` plus a bounded `history` of `{at, version, what}` are read back with `INITIAL_VERSION` and `[]` as defaults, so a doc written before versioning is `0.1.0` with an EMPTY history rather than a fabricated one: it has changed zero times as far as anything can know. **Only the patch position moves** — nothing here computes what a breaking change to a habit would be, and a `major` that never increments is more honest than one incremented on a guess.
    - **It bumps when the FILE moves, and never on a read.** A hand edit, a prose regeneration, a confirmed re-bind, a merge, and `refreshSnapshot` finding the record changed underneath it. **Not** pinning and **not** archiving: those change how the app lists a habit and not one byte of what it hands an agent, so versioning them would make the number stop meaning "this artifact moved". It is rendered as `metadata.version` in frontmatter and printed by `list_habits`, because the consumer that needs it most is an agent holding a cached copy of the catalogue.
  - **TWO HABITS ON ONE LIVE ROUTE ARE DISCLOSED, NEVER AUTO-MERGED.** A re-index re-keys every route, near-miss clustering merges two of them, a disclosed re-bind is confirmed — three ordinary paths to two files describing one procedure, which is the duplicate explosion that makes a habit library stop being worth reading. `duplicateHabits` (`habit-bind.ts`, pure) groups the ACTIVE habits by their **live** route key, not their stored one: two habits bound at different times to keys that have since merged are exactly the interesting case, and comparing what they were bound to would miss it. An orphan answers to no route and is skipped, or every unbindable habit would report as a duplicate of every other.
    - **A merge is a HUMAN act, and it destroys no writing — twice over.** The loser is **archived, not deleted**, *and* its prose is carried into the keeper verbatim under `## Also written for this route` naming where it came from. `AUTHORED_TABLES` exists to say that prose is the one thing in this repo nothing can remake, so choosing between two descriptions of one procedure is a judgement, and the app says what it found and stops — `bindHabit` declining on a tie, one level up. `mergeHabits` refuses unless both are active and both resolve to the same live route; merging habits about different work would be a data loss the app performed on its own reading of a screen. The keeper is marked `edited`, so regenerating its prose warns before discarding what was just carried over.
    - **`npm run probe:merge` is the ONLY check on any of this, and it writes to a COPY.** `deskrag-service.ts` imports `electron`, so the root suite cannot construct it: `bumpVersion`, `duplicateHabits` and `mergedBody` are unit-tested and the wiring between them is reachable from nowhere else — which is where a bump was computed and then not written, caught by reading the file rather than by running anything. The probe clones `<userData>` (APFS copy-on-write, so `lance/` costs nothing), launches the app with `--user-data-dir` at the clone, stages a duplicate the way one really arises — a confirmed re-bind — merges it, and deletes the clone. Staging two duplicate habits in the REAL store and archiving one would do to a person's authored prose exactly what `AUTHORED_TABLES` exists to prevent.
    - **A duplicate is not a `HabitBindState`.** Both bindings are exact and correct; what is unresolved is that two files claim one route. So it bands into Needs attention and chips as `duplicated` on its own check, rather than being folded into a state machine that describes something else.
  - **A dismissal is a real row.** A rejected proposal that is not persisted comes back on every load.
  - **A reflection reaches a habit as an OPINION and can never reach the record.** `HabitBrief.reflections` carries the notes from the recordings a route was built from, ordered by recording, and `habitPrompt` prints them last under a heading that says they are a model's reading of how the session went and **not part of the record**. That label is load-bearing: it is model output being fed back to a model, so without it a note that hallucinated a keyboard shortcut would be laundered into the prose as though the recording showed it. The record itself is untouchable either way — `recordedBlocks()` takes the route and nothing else. A session with no note contributes **nothing** rather than a placeholder: "no reflection was written" is a fact about the indexing configuration, and telling a model about it invites prose about the tool instead of about the work.
- **A PROMPT COMPARISON HERE NEEDS 3+ SEEDS, the same rule composing already carries.** `HABIT_SYSTEM` and `REFLECTION_SYSTEM` are the two prompts a change to habit quality is tempting to make, and the composer's own history is the warning: prompt tweaks against composition quality have twice measured as NOISE on a single run. One A/B against one recording is a coin flip with a narrative attached. Run it across three or more, report a ranked number, and say which recordings.
- **Generation is ONE model call on demand, and `generateHabit` must not call `buildProviders()`.** That resolves ONNX weights, opens the out-of-process host and can download half a gigabyte for a call that needs a chat endpoint. `buildProseWriter()` reads `summaryProvider`/`ollamaSummaryModel`/`ollamaHost` and nothing else, reusing the SUMMARY model rather than adding a picker — naming a composed level and naming a recorded flow are the same act at two altitudes. It is deliberately **not** an indexing stage: `index-plan.ts` is a table the re-index runs whole, so a habit stage would rewrite user-edited prose on every rebuild, and the queue's purge is `purgeDerived`, which must never reach an authored row. It can never fail — an unreachable daemon degrades to the template and says so in `generateNote`.
  - **`Capabilities` gains no member for this.** It reports booleans, but the screen needs the model's NAME for its disclosure, and a boolean there plus a name here would be two answers to one question. `HabitsDTO.prose` is the single source.

- **`ensureToolPath()` runs before anything can spawn** (`main/tool-path.ts`, called at module scope in `index.ts`). A packaged macOS app is launched by launchd, not a shell, so it inherits `/usr/bin:/bin:/usr/sbin:/sbin` with **no Homebrew** — and every capture/transcribe subprocess is looked up by bare name. `ffmpeg` and `whisper-cli` therefore appear uninstalled in a packaged build while working fine in a terminal-launched dev run, which is the single most confusing failure mode here. Inherited entries stay first, so a user PATH still wins.
- **The mic entitlements are INERT on an unsigned build.** `hardenedRuntime: true` + `entitlementsInherit` (`build/entitlements.mac.plist`) are what let the bundle's microphone grant reach the *child* ffmpeg that actually reads the device, and `NSMicrophoneUsageDescription` is what makes macOS show the prompt at all — but entitlements only take effect when the app is signed. Without a signing identity electron-builder skips signing and the packaged app cannot record audio no matter what the plist says. Verify with `codesign -d --entitlements - <app>`, not by reading the yml.
- **The mic is requested at Record, not at launch.** ffmpeg reads the device in a child process, and an ungranted device fails with a bare avfoundation `Input/output error` that looks like a broken build. `startRecording` requests first, so the system dialog appears at the moment it makes sense, and a refusal **drops the audio signal** rather than pretending to record it.
- **Bytes don't go over IPC.** Keyframes are served by blob id through the privileged `deskrag://frame/<blobId>` protocol (`main/protocol.ts`), registered *before* `app.whenReady`.
- **`SettingsStore` holds no secrets** — every provider is local, so there is no key, no `safeStorage`, and no `keys.enc`. It deletes a stale `keys.enc` on open rather than leaving unreadable ciphertext on disk. A persisted provider value outside its allowed set (`PROVIDER_VALUES`) resets to the default instead of being carried forward, so settings can never name a provider the app cannot construct.
- **Data dir:** `<userData>/DeskRAG/` (dev: `~/Library/Application Support/deskrag-app/DeskRAG/`) — `app.db`, `lance/`, `blobs/`, `models/`, `settings.json`. `DualStore.listSessions()` is the authoritative session list (SQLite, with per-session counts + the `screen` video blob id), so the Library list can't drift from what delete actually removed. There is no `sessions.json` sidecar — an old one left on disk is ignored.
- **Trace indexing is the last stage, and `main/trace-index.ts` is the only place `trace/` meets the store.** `liftTrace` takes its world through injected callbacks precisely so `src/trace/` stays a leaf; that module binds them. All three environment callbacks resolve **latest at-or-before the `t_mono`** from the session's own event stream, which is why topology and layout are recorded as events at all. It runs after Regions (`regionsAt` reads what that stage wrote) and after Segmenting (boundaries define the nodes). Every session merges into **one graph** (`DEFAULT_GRAPH_ID`), which is what makes a second recording of a task branch or fill a slot instead of starting a disconnected chain — `mergeTrace` seeds a new graph's id from the session, so the id is pinned on write.
- **`KeymapProducer` is wired to the input signal, not its own toggle.** Without it nothing emits a layout, `resolveKeys` has nothing to apply, and every text gesture is dropped — so a recording with keys but no keymap silently loses all typed content. The Trace stage says so in its progress label rather than only in the console, because nothing else would tell the user.
- **Deleting a recording is two calls, in order:** `store.deleteSession(id)` then `blobs.removeSession(id)`. The store records where blobs are; it does not own the files. Rows first — a row pointing at a deleted file is a broken read, whereas a file with no row is just reclaimable disk.
- **Video is served over a separate protocol host.** `deskrag://frame/<blobId>` buffers a keyframe whole; `deskrag://media/<blobId>` streams with `Range` → `206`. Chromium will not let a `<video>` seek without the 206 + `content-range` path.

- **The MCP endpoint (`app/src/main/mcp/`) is the only way anything outside the app reads the index, and it is READ-ONLY BY CONSTRUCTION.** Eleven tools — `search_experience`, `get_moment` (the keyframe as an MCP image block), `list_recordings`, `get_recording_outline`, `list_flows`, `get_flow`, `list_habits`, `get_habit`, `search_habits`, `get_habit_step`, `get_habit_steps` — hosted by the app over stateless Streamable HTTP on `127.0.0.1:41777`. It reuses `DeskRagService` verbatim, because that is the single owner of the store and the providers: a standalone stdio binary would be a SECOND owner, duplicating `buildProviders` wholesale and opening SQLite and LanceDB behind the app's back. The cost, stated: the app must be running.
  - **`test/mcp.readonly.test.ts` is the whole safety story**, the same principle as `test/replay.barrel.test.ts`. No file under `mcp/` may import `replay/`, name `ax-exec`, spawn, or call `startRecording`/`removeSession`/`reindex*`. It reads CODE — comments are stripped, and the stripper is itself tested, because it first fired on a comment *discussing* `ax-exec` and a guard that trips on the discussion is one the next person deletes. **`close` is deliberately not guarded by name** (it is the HTTP server's and the transport's method too); closing the STORE is prevented by TYPE, since the reader holds a `ServiceReads` port that does not declare it.
  - **THE HOST CHECK IS WHAT CLOSES DNS REBINDING; the Origin check cannot.** Once `evil.example` has rebound to 127.0.0.1 the browser considers the target same-origin and sends **no Origin header at all** — only `Host: evil.example` gives it away. Both run, Host first, ahead of the method and the path so a rebound page cannot even learn the route. Verified against the live socket: cross-origin 403, rebound Host 403, GET 405. Note `fetch` **cannot** forge Host (a forbidden header), so the test uses node's raw client — a restriction a real browser does not have.
  - **`get_habit` returns the HABIT.md RAW, with no preamble**, and that is the one place this surface deliberately does not explain itself. The value of the tool is that its output IS a file; a sentence in front of the `---` corrupts a paste to disk, and everything a client needs in order to weigh it is already inside the document (`metadata.prose`, `metadata.recordings`, `metadata.steps: template`). `list_habits` carries the framing instead, and puts RECORDED ONCE and ORPHANED in the LIST — an agent decides from the catalogue whether to fetch at all, so a disclosure that only appears in the file arrives too late to change that decision.
  - **`list_habits` names the routes NOBODY has kept, because recurrence is the only evidence a proposal carries.** The proposals branch used to sit entirely inside the `kept.length === 0` empty state, so the moment one habit was kept the catalogue stopped reporting that other routes had been walked four times each — the very thing that makes one worth keeping. `candidateBlock` appends them after the kept habits (what the user has established is the answer; what nobody has kept is context for it), and partitions by recurrence exactly as `lines()` does one level down: routes walked more than once are NAMED with their count, routes walked once are COUNTED and never named. Counting rather than dropping keeps the disclosure complete; naming a singleton beside a repeated route would present an observation as a habit. `preview` is never printed — it is a whole rendered record and would dwarf the catalogue.
  - **Habit PERSISTENCE is on neither `ExperienceReader` nor `ServiceReads`.** Keeping, editing, regenerating and forgetting all go through `DeskRagService` and IPC, so the guard's type-level promise is unchanged: a tool structurally cannot author a habit even though the app can. `mcp/habit-text.ts` renders the catalogue only, and the readdir guard covered it the day it landed.
  - **There is deliberately NO token**, a decision taken with the risk on the table: any local process can read the whole index, and typed text is not redacted (`buildDigest` folds it in on purpose). The gate is instead the visible activity log in Settings. Both facts are stated in the pane, not just in the spec.
  - **A bind failure is reported, never retried onto another port** — the user has already pasted a fixed URL into an agent's config, so a server that quietly moved presents as broken. `enabled` and `listening` are separate fields for this reason.
  - **The low-level `Server` is used, not `McpServer`**: `registerTool` types `inputSchema` as Zod, which would put Zod inside `tools.ts` — pure, SDK-free and root-tested so the tool surface can be argued about offline.
  - **`search_experience` SHOWS NO SCORE, for the reason in the retrieval section above**: the top hit of every query sits at the ceiling, so an agent handed the number reports "100% confidence" to a user. It prints the evidence lanes instead, and one preamble stating that the ranking is relative to this result set — dropping "best first" entirely when the hits are tied, since the order is then arbitrary. Same class of failure as the empty-result branches below: a technically-true output an agent will confidently misreport.
  - **An empty search result is the shape of three different states.** `indexedUnderDifferentProvider` and `segmentsMatchedButNoFrames` are rendered as prose; a bare empty list makes an agent report "you never did this" when the truth is a namespace mismatch.
  - **Confirmed on a real store (2026-08-13), in the DEFAULT configuration (`imageProvider: "none"`)**: 13 recordings, search returning real hits at score 1.000 (which is the *ceiling* of that configuration, not a perfect match — see the score note above), a full `SESSION → PROCESS → TASK → ACTION` outline, six recorded routes, and a 275 kB keyframe over the wire. `npm run probe:mcp` re-runs all of it.
  - **Re-confirmed 2026-08-23 at eleven tools**, on a store of 8 recordings, 5 routes and ONE kept habit. That corpus is the point rather than a limitation: it is the case `search_habits` was designed around, and `probe:mcp` checks the disclosure fires — the reply says the one habit is the only candidate rather than presenting it as a match. `get_habit_step`'s multi-way refusal is reachable here too, because the kept habit binds to `Calculator → TextEdit`, which `probe:fork` reads at four ways; the probe drove it and got the four letters named. It also caught a defect in ITSELF: its `no score printed` check read false against a real habit at `v0.1.10`, because a semver matches the shape of a score. The suite's fixture sits at `v0.1.0` and could never have shown it.
- **Lifecycle:** window close hides to a menu-bar tray and recording keeps running; only Quit closes the store.
