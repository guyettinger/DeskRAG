# Model providers, tiling, and patch highlights

Why every provider is local, why text embedding left Ollama for a pinned ONNX menu, what standardizing on ColModernVBERT removed, and the geometry behind a highlight box.

> Moved out of `CLAUDE.md` on 2026-08-15, verbatim. Every number here is a measurement
> taken from a real recording or a real run — not an estimate. Re-measure before changing one.

**Every provider is local — there are no cloud adapters and no API keys anywhere in this repo.** Adapters either talk to a daemon on localhost (Ollama), run the model in-process (ONNX), or spawn a subprocess (whisper.cpp, ffmpeg, the Swift AX sidecar). A network call to a third party is a regression, not a feature to add. Anything that embeds/captions/reads-AX is still behind an interface with swappable adapters and a **deterministic fake** for tests — that seam is what makes the suite offline and deterministic, and it stays open even where only one local implementation exists.

Adapters that **load a native npm module** (`onnxruntime-node`, `uiohook-napi`, `active-win`, `sharp`) are **deliberately NOT re-exported from `src/index.ts`** — import them from their own path — so importing the package never force-loads native code. The line is **native module, not subprocess**. Everything that merely spawns a binary is exported and always has been — the Swift sidecar sources (`SwiftAxSource`, `SwiftDisplaySource`, `SwiftKeymapSource`) and the ffmpeg producers alike — because importing them loads nothing until they run. The whole visual/native chain is real and tested; only query vectors are faked (a fake embedder maps identical input → identical vector, which lets tests place exact-match items deterministically).

**TEXT EMBEDDING IS ONNX-ONLY, AND THE MODEL IS A PINNED MENU.** `TextProvider = "ollama" | "onnx"` and the free-text `ollamaModel` beside it are both gone; `textModel` picks from `TEXT_MODEL_SPECS`, and Ollama keeps captions and summaries only. The consequence worth stating plainly: **a default install now searches text with no daemon running at all**, where the previous default put one between every query and every text result.

The free-text box was not a theoretical hazard. Measured on **LIB-14** (see below): `vector_space` held `digest:ollama:muse-glimmer:768` and `digest:ollama:muse-glimmer:30b-mlx:768` — a 30B chat/vision model typed into the embedding field — and one of them had minted `digest__ollama__muse-glimmer__768.lance` declaring `FixedSizeList[768]` before the add failed. **Two dead vector spaces, zero rows, and nothing on screen to say so.**

> **LIB-14** is the store every number in this section was taken from: the author's
> library as it stood on 2026-08-16 — 14 sessions, 849 segments, 750 of them
> carrying a digest — indexed through `ollama:nomic-embed-text`. It was **reset and
> re-indexed on that same day** onto `onnx:embeddinggemma-300m`, so it no longer
> exists and none of these figures can be reproduced by reading the current store.
> They are recorded because the TRAPS are durable, not the digits. Re-measure with
> `npm run probe:embed` before quoting any of them as current.

- **A DROPDOWN OVER `/api/tags` WOULD HAVE SHIPPED THE SAME BUG WEARING A `<select>`.** `OllamaTextEmbedding` hardcodes `dimensions: 768` (`src/embed/ollama.ts:30`) and `buildProviders` never passed one, so **every 1024-dim model on that menu** — `bge-m3`, `qwen3-embedding`, `mxbai-embed-large`, `snowflake-arctic-embed2` — mints a namespace claiming 768 and then fails at `lance.add`. The dimension has to be **declared**, and that is the whole argument for pinning the menu rather than discovering it.
- **A model's quirks are DATA (`src/embed/text-profiles.ts`), and all of them fail SILENTLY when guessed.** Task prefixes (nomic's `search_document: `/`search_query: ` vs EmbeddingGemma's `title: none | text: ` and `task: search result | query: `); whether `token_type_ids` is required — **nomic's export REQUIRES it and Gemma3 REJECTS it, so no single value satisfies both**; and which output tensor carries the embedding. The profile is barrel-safe plain data so the app's download manifest reads the same values the adapter runs on instead of restating them beside a URL.
- **EmbeddingGemma's export emits BOTH `last_hidden_state` AND `sentence_embedding`, and only the second is the model.** The ONNX graph traces the full sentence-transformers pipeline — mean pooling, **both** Dense heads (`2_Dense/`, `3_Dense/`), normalization. Mean-pooling `last_hidden_state` instead, which is what "just take the output" does, yields a vector that is 768 wide, unit length, one row per input and deterministic across runs — and **cosine −0.0229** against the real embedding, where the correct output scores **0.9938**. It is orthogonal. No structural assertion can see this, so `test/onnx.smoke.test.ts` compares against Ollama's independent f16 build of the same weights; the floor is 0.98, not 1.0, because q8 ≠ f16.
- **`onnx-community/embeddinggemma-300m-ONNX`, not `google/embeddinggemma-300m`** — the upstream repo is `gated: manual` and the app downloads anonymously, so the official weights are unreachable, not merely inconvenient. `model_quantized` (q8, 309MB) rather than `model_q4f16`: **EmbeddingGemma's activations do not support fp16**, which rules out every f16 variant. Both `.onnx` and `.onnx_data` are pinned — the `.onnx` alone is a 568KB graph — and they resolve after `ModelStore` flattens to basenames, which was verified by loading the pair rather than assumed.
- **`npm run probe:embed` picks the default, and its FIRST VERSION MEASURED NOTHING.** It scored "did the model return this exact segment id" against **LIB-14**, where 750 segments carried a digest and only **144 were distinct** — `"Calculator — Calculator. 1 click. clicked in Calculator."` appeared **85 times** — capping top-1 at 1/85 for that query and reporting a 28.6% MRR "lift" that was entirely noise off an unreachable ceiling. Identical documents are one document; a tied duplicate is not an error. The RATIO is the durable part and any desktop capture will have one: a digest is a window title plus a gesture, so a corpus of them is mostly repeats. Corrected, 150 cases over seeds 7/11/23/42 on LIB-14: nomic top5 22.0–23.3% / MRR 0.128–0.139, EmbeddingGemma top5 25.3–26.0% / MRR 0.162–0.165.
- **EmbeddingGemma wins every metric on every seed and is still NOT the SHIPPED DEFAULT.** The lift is 18–27% relative MRR, but it costs **3.3x** the indexing time and **+370MB resident** (measured under the Electron smoke, which is machine-independent in a way LIB-14 is not: 0.2s → 0.6s per 16-text batch, rss 1.35GB → 1.72GB), and a top5 of 26% is not a lane worth stranding every text vector on disk for. Its context is also **2048 tokens against nomic's 8192**, which truncates long transcript clips sooner. Revisit on a corpus less dominated by one Calculator window — LIB-14 was exactly that corpus, which is the strongest caveat on its own numbers.
- **The end-to-end path IS verified on a live store, and that is separate from the bake-off.** After the 2026-08-16 reset, one session re-indexed on `embeddinggemma-300m` produced seven correctly-namespaced spaces, no `ollama` text space and no orphans, with digest 42 / caption 34 / summary 4 / transcript 19 rows. A query embedded at `role: "query"` against the STORED document vectors returned `clicked "All Clear"` top for "clicked all clear" at **0.610 against 0.399** for the next hit — which is what proves index-time and query-time share a space. Mismatch the prefixes across roles, or read a different output tensor on one side, and that separation is the thing that disappears.
- **Retiring the lane DISCLOSES and does not act.** A persisted `textProvider: "ollama"` surfaces as `EnvInfo.migratedTextProvider` and a Settings banner saying the text, caption, transcript and summary lanes all need a re-index; nothing is started for the user. An install already on `"onnx"` is deliberately **silent** — its vectors are in `*:onnx:nomic-embed-text-v1.5:768`, exactly what `textModel` defaults to, so it lost nothing and telling it to re-index would be a lie.

**THERE IS ONE IMAGE PROVIDER: `colmodernvbert`, OR `none`.** The menu had four (`none`, `nomic` single-vector, `colsmol`, this) and the bake-off that produced it is over. Standardizing removed far more than two adapters, because **Nomic Vision was the only `ImageEmbeddingProvider` in the tree**: deleting it stranded the entire single-vector image lane, and all of it went — `frame_image` and `region_image` as VIEWS, `Tier2Retriever`, Tier 3's ANN half, `FrameRepresenter`, the crop-and-embed half of `RegionRepresenter`, `putFrameVectors`, `searchFrames`/`searchRegions`, the `frameEmbeddings` stage, `scripts/export-colsmol.py` and a 953MB download entry. `TableKind` is now `"segment" | "frame_patches"`, `MissingVector.entity` is `"segment"` only, and `VecRow` has one member.
- **NOTHING A ColModernVBERT INSTALL COULD DO WAS LOST, and that was checked rather than argued.** Region rows, bboxes, AX role/label and `region_fts` all survive, because the `regions` stage gate is `always` and it now runs **proposal-only under every configuration** — so Tier-3 AX-label FTS, the digest's "label of what was clicked", `Anchor.visual` in the trace graph and the rail's `regionCount` are untouched. On the multivector path Tier 3 was **already** deliberately FTS-only. Confirmed by driving the real app: with `imageProvider: "none"` a text query returns 30 hits and `DetailView` draws the AX-label box ("Start recording"); with it set, 7 boxes — 6 patch, 1 labelled.
- **`colsmol-tiler.ts` was RENAMED `idefics3-tiler.ts`, and `geometry.ts` stayed**, because both are the Idefics3 processor's geometry rather than one model's. `readTileConfig` accepts BOTH spellings of `pixel_shuffle_factor` (top level here, under `text_config` in ColSmol's) — a reader that knew only one falls through to `DEFAULT_TILE_CONFIG`, which is also 4, so it would be **right by luck**.
- **The `MEASURED` table in `test/onnx.geometry.test.ts` was taken from ColIdefics3Processor and is STILL VALID, checked not assumed.** The two `preprocessor_config.json` files are byte-identical apart from `processor_class` (same `Idefics3ImageProcessor`, 2048/512, mean/std 0.5) and both `config.json`s declare patch 16, shuffle 4. Confirmed against the real export too: the Electron smoke embeds a 2560x1600 fixture and reports `4x3 + global = 13 tiles`, `vectors=832`. `scripts/dev/dump-idefics3-processor.py` regenerates it (needs `colpali_engine`, which is not installed here).
- **The ONNX contract is THREE inputs, not four** — no `pixel_attention_mask`, because Qdrant's wrapper builds `input_ids` from the actual patch count instead of masking a padded batch. That is also why it needs no re-trace at a fixed tile count.
- **The tokenizer wraps every encode in `[CLS]` … `[SEP]`** (ModernBERT, not SmolLM2), `<|begin_of_text|>` is NOT in its vocab (ten BPE tokens, not one), and the last grid row's `"\n"` abuts the global block's leading `"\n"` so BPE merges them into ONE token — 884 tokens for a 1280x800 frame, not 885. A query's ten buffer tokens go INSIDE the wrapper, because fastembed augments the query STRING and then encodes. `test/onnx.smoke.test.ts` re-encodes fastembed's exact string and compares it to `buildImagePrompt` element by element; that is the check that pins every constant, not the per-token one.
- **A persisted `"nomic"`/`"colsmol"` MIGRATES to `"colmodernvbert"`, not to the `none` default** (`PROVIDER_MIGRATIONS` in `app/src/main/settings.ts`, consulted BEFORE the reset-to-default loop). Same justification as `audioDeviceFor`'s `":0"`: only a previous BUILD could have written either string. `"none"` says the user wanted no visual search; these said they wanted the best one available. The cost is disclosed rather than hidden — `EnvInfo.migratedImageProvider` puts a banner in Settings saying a re-index is needed.
- **`DualStore` DROPS RETIRED SPACES ON OPEN, and that is destructive and rehearsed.** `purgeRetiredSpaces()` runs once in `open()` over any space whose view is not in `VIEWS` (`RETIRED_VIEWS`) or whose model is in `RETIRED_MODELS` (`colsmol-256m` — its view is `frame_patches`, so a view check alone would leave its table answering nothing). `LanceStore.dropSpace` is a **no-op when the table is not on disk**, the rule `deleteByIds` already had to learn. It reports rather than logs (`retiredSpacesPurged`), because `store/` prints nothing. **Rehearsed on a copy of the real 14-recording store**: 3 spaces dropped (`frame_patches:onnx:colsmol-256m:128`, `frame_image:…`, `region_image:…`), 11 Lance dirs → 8, and every captured and derived count identical — session 14, event 5735, frame 604, region 8419, segment 860, ax_snapshot 751, trace_edge 114.
- **`parseNamespace` REJECTS a retired view, and that is safe only because opening a store does not parse.** `DualStore` reads the `view` COLUMN; the sole caller of `parseNamespace` is `ensureTable`, on a namespace being registered. A store on disk holds a 5-part namespace (`digest:ollama:muse-glimmer:30b-mlx:768`) that `parseNamespace` also rejects, and it opens fine. Throwing on open is what took down a whole re-index once.

**SCORING KEEPS EVERY QUERY VECTOR; HIGHLIGHTING KEEPS ONLY THE CONTENT ONES.** A ColPali-family query is the user's tokens plus ten `<end_of_utterance>` buffer slots, wrapped in `[CLS]`/`[SEP]` for ColModernVBERT. MaxSim needs all of them — the buffer slots are learned expansion slots — so `QueryEmbedding.vectors` still goes to `searchFramePatches` whole. Highlighting must not: measured on a real frame, `"probe mcp"` is **15 vectors of which 12 are wrapper or buffer**, and one box per query-vector argmax drew seven boxes of which four were noise, with `[CLS]` scoring **0.992** against blank document space and therefore ranking FIRST. `QueryEmbedding.contentIndices` is how the provider — the only thing that knows its own prompt layout — says which is which; `queryContentPositions` lives beside each `buildQueryPrompt` because the two layouts genuinely differ. `highlightsFrom` then scores a map over GRID patches (the global tile leaves the map up front rather than costing a slot after the cap), floors it at `DEFAULT_RELATIVE_FLOOR` and merges 4-connected survivors into one box each. **The floor is a measurement**, swept by `npm run probe:highlight` over 10 known-answer queries on 6 frames across 6 applications; 0.80 is the knee, and the honest part is that only ~22% of boxes land inside the answer at ANY floor — a patch map attends broadly and no floor makes it precise.

**THE HIGHLIGHTER READS THE PROVIDER'S GEOMETRY, NEVER `DEFAULT_TILE_CONFIG`.** `MultiVectorProvider.tileConfig` is REQUIRED, the `contentIndices` precedent: the provider is the only thing that knows its own layout, so it is the only thing that should state it. The numbers coincide for ColModernVBERT, which is exactly the problem — the default was **right by luck** and would have gone on looking right, with every box on the wrong part of the frame and every score plausible, the moment an export changed its tiling. Only a fake declaring a DELIBERATELY different config can tell the two apart, which is why `FakeMultiVectorProvider` takes one.

**A GRID DISAGREEMENT DRAWS NO BOXES AT ALL, rather than truncating to the smaller count.** `gridCount = Math.min(gridTokenCount(geo), patches.length)` absorbed it silently. The geometry is recomputed from `frame.width/height`, which are **screen points** (1920x1080, from `screen.getPrimaryDisplay().size`), while the embedder tiled the **JPEG** (2560x1440) — and the JPEG's dimensions are stored nowhere (`FrameRow` has only points, `BlobRow` has no dims). They agree today only because the grid depends on ASPECT RATIO alone. `highlightsFrom` now compares `expectedTokenCount(geo)` against `patches.length` and returns `[]` on disagreement: the grid is wrong, so every box would be wrong, and a wrong box is worse than no box. Deliberately NOT fixed by persisting JPEG dimensions — there is no migration mechanism, a new table would be empty for every existing frame, and the count check catches the same class of error against ground truth already on disk. Consequence for tests: `FakeMultiVectorProvider.embedImages` emits a **geometry-consistent** patch set (832 for its declared 1280x800), not a fixed small count.

**THE GEOMETRY IS EXACT, AND THE MEASUREMENT THAT SAYS SO IS NOW COMMITTED (`npm run probe:patchgeom`).** The earlier one was thrown away, and it measured the wrong statistic: it painted a 320x240 rect and reported the top changed patches as "inside it or within two patches of its edge" — but a patch cell is ~60x45 frame px, so two patches is ~120px of slop, which cannot tell an exact mapping from one off by half a cell. **DISPLACEMENT is the right statistic**: signed, in cells, and each value of it names a different function (±0.5 → `cellToBox` centre-vs-corner; ±1.0 → `patchIndexToCell` ordering; growing with distance → `scaleX`/`scaleY`). `scripts/probes/patch-geometry.ts` paints a marker at a known frame-space cell, re-embeds with the real ColModernVBERT, and compares the argmax and a score-weighted centroid against the truth. **Measured 2026-08-14 over 36 markers on two real frames of different aspect ratio (1920x1080, 1728x1117), 2 sizes x 9 positions:**

| marker | argmax Δcol / Δrow | centroid@8 Δcol / Δrow | argmax |
| --- | --- | --- | --- |
| 1x1 (18) | +0.67 / −0.28 | +1.86 / +0.06 | **exact cell 14/18** |
| 2x2 (18) | **+0.00 / −0.33** | **+0.30 / −0.07** | contained 13/18 |

Slope of Δ against position: **−0.06 / −0.01 cells/cell**, i.e. no scale error. Read the 2x2 row: its truth sits BETWEEN cells, so ±0.5 is the best an integer argmax can do and its centroid is the number that means something — every |mean| is under half a cell. The 1x1 row's argmax is exact 14 of 18 times (the 4 misses all had a near-zero top delta: the marker landed on content it barely changed), while its top-8 centroid is mostly noise because only ~1 patch genuinely moves. **So the visible offset in a highlight is the model's own 60x45px resolution and its broad attention, not a mapping error.** Do not "fix" `patchIndexToBox` when a highlight looks misplaced; re-run this probe first.

**AND THE BOX THAT ACTUALLY MOVED WAS A FLOAT16 DECODE.** `getFramePatches` ran Arrow's `Vector.toArray()` on the float16 `patches` column, which returns the raw **uint16 BIT PATTERNS** — 11569 where 0.0811 was written. Nothing errors: right row count, right vector length, plausible cosines, so the ONLY symptom is highlight boxes landing on arbitrary parts of the frame. Measured on the reported frame, the app's boxes ranked **421–748 of 768** under a correctly decoded embedding, i.e. near-random, while the same code fed correctly decoded patches put its three brightest boxes on the `mcp` tab, the `mcp` sidebar entry and `probe:mcp` in a shell command. **ITERATE an Arrow vector, never `.toArray()` it.** The round-trip test that "covered" this asserted only `length` — the same read-the-row-count-not-the-bytes failure as the silent microphone. Retrieval never went through that reader (`searchFramePatches` does its MaxSim inside Lance), so this was a highlights-only defect.

Two shared helpers keep the local adapters from duplicating each other, and new adapters should use them rather than re-rolling: `src/embed/onnx/tokenizer.ts` (`loadTokenizer` / `defaultConfigPath` — the `@huggingface/tokenizers` load that text, late-interaction and reranker adapters all need, minus the encode shape, which is the part that genuinely differs) and `src/embed/ollama-client.ts` (`resolveOllamaHost` / `postJson` / `listModels`). The Ollama client deliberately does **not** own failure policy: `OllamaTextEmbedding.embed` throws (a missing vector must not look like a clean write) while `OllamaCaptionProvider.caption` returns `""` (a missing caption is recoverable by reconciliation). `listModels` sources from `/api/tags`, never a hardcoded list — Ollama's *library* now includes cloud-hosted models, and offering one in a "local" picker would route screenshots off the machine. That is a structural guard, not a style choice.
